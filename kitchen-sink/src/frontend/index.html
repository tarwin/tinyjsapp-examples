    ⤢ toggles · on/off set an absolute state
    setPosition — top-left origin

    setAlwaysOnTop — the window floats above other apps' windows, even unfocused. What a palette, a HUD or a picker-in- progress wants. setLevel() goes further, putting a window above fullscreen apps or down on the desktop.

    setResizable — turns off the user's ability to drag the edges. Your own setSize() still works, so a fixed-size window can still resize itself. Pair with setMinSize() when you want a floor rather than a lock.

    setHideOnClose — the close button hides the window instead of quitting the app, which is how a tray or menu-bar app stays alive with no window on screen. Bring it back with win.show() — usually from a tray click or a hotkey.

    Where the window sits setLevel · setAllSpaces · setClickThrough

    setAlwaysOnTop is one point on a scale, not the whole of it. These three are what turn a window into an overlay: which band of the screen it stacks in, whether it follows you between desktops, and whether it takes the mouse at all. Nothing here shows up in getState() — they're properties of the window server, not of the window — so the way to check one is to look at the screen.

    setLevel — four bands. floating is what setAlwaysOnTop(true) sets: above other apps, below fullscreen ones. overlay goes higher still — on macOS it clears fullscreen apps and even Mission Control, which is where a screen annotator or a "now recording" chip lives. desktop drops the window behind everything, onto the wallpaper: pets, clocks, visualisers. Windows and Linux have two bands rather than four, so overlay lands on the same topmost as floating there.

    setAllSpaces — the window joins every desktop instead of belonging to the one it was opened on, so switching Spaces brings it along and it floats over fullscreen apps. The pairing for a HUD is this plus setLevel('overlay'). macOS and X11 do it; it's a no-op on Windows, and Wayland has no concept to map it to.

    setClickThrough — the window stops receiving mouse events entirely and they land on whatever is behind it. That's what makes a transparent overlay usable: you can see it and still work through it. It also means the page can't switch it back off, since your click never arrives — so this button turns it on for four seconds and the timer turns it off. A real app pairs it with a hotkey or a tray item, never with an in-window button.

    try desktop, then click another app — this window drops behind it and stays there

    A floor, and a zoom setMinSize · setZoom

    Two ops about size that aren't setSize: one stops the window getting too small, the other changes how big everything in it looks without the page knowing.

    setMinSize(w, h) — a floor under user resizes. Set it, then grab the window's bottom-right corner and drag inward: it stops. It's for layouts with a natural minimum, where being dragged smaller doesn't reflow, it just pushes controls off the edge. win.open() takes the same thing as minSize: '900x640', so a satellite window can be born with it. Your own setSize() still goes under the floor on macOS — the button above proves it — while GTK clamps both; if the floor has to hold against your own code too, check the size before you set it.

    setZoom(factor) — native page zoom, rendered by the webview, so text stays crisp at any factor instead of being a scaled bitmap. The page has no idea: it keeps laying out in CSS px, and simply has fewer of them to work with — watch innerWidth halve at 2×. That's the difference from a CSS transform: scale(), which zooms a fixed layout. For a real "double size" mode, pair it with setSize(w × f, h × f) so the window grows to match.

    The menu bar tiny.menu.set — declare it once, clicks come back by id

    One call replaces the whole menu bar: an array of { title, items }. Items are { id, label, key?, checked?, enabled?, submenu? } or { separator: true } — and that same item shape is what the tray and right-click menus take, so you learn it once.

    There are no per-item callbacks. A function can't cross the bridge, so every click anywhere in the menu bar comes back as an id to a single tiny.menu.on handler. That's why the ids are worth naming deliberately — this deck routes tab:media and friends straight through it, which is why View works at all.

    The View and Actions menus at the top of your screen are made exactly this way. Add a third and watch the real menu bar change — note that "adding" one means sending the whole bar again, since set replaces rather than appends.

    it carries a ⌘J shortcut, a checkmark, a submenu and a deliberately disabled item

    Window chrome 0.7.0 · reshape the native window, live

    tiny.win.setChrome({ frame, windowControls, transparent, vibrancy }) — native resize, focus and fullscreen keep working throughout. A packaged app can bake the same shape into tinyjs.json ("chrome": {…}) so it applies before first paint, with no titlebar flash.

    frame — turn it off and the window loses its titlebar. The deck's own header takes over: it carries data-tiny-drag, so dragging it moves the window and double-clicking zooms. Buttons and inputs inside a drag region are excluded automatically.

    windowControls — the close / minimize / maximize group (macOS calls them traffic lights). Pass true or false for all of them, or an array like ['close'] for a subset. macOS hides each one individually; Windows maps them onto window styles, where the min/max boxes need the system menu, so dropping close drops the others too; Linux can only hide close portably and asks the WM for the rest.

    transparent — lets the desktop show through, but only where the page background has alpha. A page painted a solid colour looks exactly the same with this on.

    vibrancy — macOS's frosted-glass material: the window blurs and tints whatever is behind it, the way Notification Centre and the Finder sidebar do. Needs transparent on to be visible, since it renders behind the page. The names are Apple's materials — sidebar is lighter, hud darker. A no-op on Windows and Linux, which have no equivalent; capabilities().vibrancy says so.

    tiny.win.setChrome(…) restyles the frame while the window keeps every native behavior — getState() reports the chrome back too (0.7.0)

    Where the app lives tray · dock / taskbar / launcher

    Two separate places an app can appear, and the words differ per platform: the tray is macOS's menu bar, Windows' notification area and Linux's AppIndicator; the app icon is the Dock, the taskbar or the launcher. tiny.tray.set() owns the first, tiny.app.presence() the second.

    Keep at least one. Turn off both and the app is still running with no way back to it — no icon to click, no menu to open. This deck switches the tray on for you if you drop the app icon while it's off; a real app should do the same, or refuse. The full menu-bar recipe is tray.set() + win.setHideOnClose(true) + app.presence('menubar') — or "activation": "accessory" in tinyjs.json for a pure agent with no launch flash (see matcha).

    tray icons take an SF Symbol by name (icon: 'sf:…', no png shipped) and primaryAction: true makes left-click toggle the window, with the menu on right-click

    Tray recipes live icons · zones · a window under the icon

    A tray item is one tray.set() call you can make again whenever anything changes — there's no separate update call, you just set it again.

    Notifications 0.6.0 · banners, actions, replies

    tiny.notify(title, body, { id, subtitle, sound, actions }) — a packaged, signed .app shows a real Notification Center banner; clicks route back via tiny.app.onNotificationClick, buttons and replies via tiny.app.onNotificationAction (dev falls back to osascript)

    What actions are: real buttons on the banner. Give notify() an actions array and each entry becomes a button; mark one reply: true and it opens an inline text field instead. Pressing either fires tiny.app.onNotificationAction({ id, action, reply }) — so the user answers a question without your app ever coming to the front. That's the point: a reply from the banner, no window, no focus change.

    Where they work. macOS needs a packaged app — UNUserNotificationCenter requires a bundle, so tinyjs dev falls back to osascript, which has no buttons at all (that's the Script Editor banner with a lone Show button). Windows and Linux notify from the launcher in every mode, so their buttons work in dev; Linux has buttons but no reply field.

        Which one should you use? SQLite vs the key/value store

        Both persist and both are one import. They fail in different directions, and picking wrong is the kind of thing you notice much later:

        tiny.store — a single JSON file, rewritten whole on every change. Right for settings: window size, theme, the last folder you opened. No queries, no partial writes, no schema — so a thousand entries means re-serialising a thousand entries to change one of them.

        SQLite — indexes, WHERE, ordering, transactions, and writes that touch only the row they touch. Reach for it the moment you have a list that grows: notes, history, a cache, anything you'll later want to search or sort.

        Rule of thumb: if you're about to write store.all().filter(…), you wanted SQLite.

        Watching the clipboard 0.22 · clipboard.changeCount / watch / onChange / unwatch

        changeCount() is the OS's own counter: it goes up by one every time anything puts something on the clipboard, whoever did it. Asking is a question, not a subscription — compare it with the last number you saw and you know whether you missed something without reading the contents, which is the polite way to poll when the answer might be somebody's password.

        changeCount() right now— changes delivered here0

        watch(ms) polls inside the launcher, in-process — no pbpaste spawn per tick — and speaks up only when the count actually moves. onChange is where those land, as { changeCount, self }, and self is true when your own write() caused it: that flag is what stops a clipboard-history app recording its own pastes forever. Press Copy from this page and watch one arrive tagged.

        start watching, then copy something in any app

        unwatch() stops the delivery, not the world. Turn watching off, copy something elsewhere, then press Ask changeCount — the number has moved on without you, and the gap says how many changes you missed (never what they were). That one number is the cheap thing to check when a window comes back or the machine wakes: it tells you whether re-reading is even worth it.

        A page's console.log goes to the webview's console — you need the inspector open to read it, and it's a different stream from everything the backend prints. tiny.log() carries the line across the bridge and prints it from the backend instead, tagged [web], so both halves of the app land in one place, in the order they actually happened.

        Look in the terminal running tinyjs dev. Whatever JSON can carry goes across, so an object arrives as an object — { n: 42 }, not [object Object] — and line breaks survive. It resolves true once the backend has the line, so you can await one before doing something that might take the process down. A packaged app opened from the Finder has no terminal attached: run its binary from one, or write your own file under app.paths().logs.

        tiny.fetch window.fetch, but the request runs in the backend

        Same signature as window.fetch, and it resolves a real Response — res.status, res.headers, res.json() all work as you'd expect. What changes is where it runs: in the backend process, so there's no CORS preflight to satisfy, no CSP to appease, and no mixed-content block. The page never touches the network.

        Note what this card doesn't do: define a backend handler. An earlier version of this deck hand-rolled one — serialising status, headers and body across the bridge by hand — which is exactly the boilerplate tiny.fetch exists to delete.
